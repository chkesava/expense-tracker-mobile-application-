# EPF in Spendly

The entry point for the EPF module. Start here; the per-ticket documents listed
at the bottom are the decision record and explain *why* each piece is the way it
is.

| | |
|---|---|
| **Product** | Spendly → Investments → EPF |
| **Epic** | [KAN-64](https://kesavach.atlassian.net/browse/KAN-64) |
| **Route** | `app/(app)/epf/[establishmentId].tsx` |
| **Pure logic** | `shared/features/epf/` |
| **Server** | `netlify/functions/epf-cron.ts` |

---

## The one thing to understand first

**Spendly cannot see EPFO.** There is no API, no scraping, no passbook import.
Every number the module shows is either something the user typed or something
Spendly projected from what the user typed.

The whole design follows from that. A single field, `reconciledAt`, separates
the two, and **only a human ever sets it** — by opening a month, a transfer or a
balance and confirming it against a real passbook. Anything without it is
labelled *simulated* or *projected* in the UI, and the dashboard says
"EPF · simulated" while any part of the figure is unconfirmed.

Nothing in the module may quietly turn a projection into a fact. That is the
rule the rest of this document keeps restating in different forms.

## Domain model

Eight collections, all under `users/{uid}/`, all created by this epic:

| Collection | Holds | Document id |
|---|---|---|
| `epfProfile` | the UAN and employee name | always `main` |
| `epfEstablishments` | one per employer | random |
| `epfContributions` | one per establishment-month | `{establishmentId}_{YYYY-MM}` |
| `epfContributionEvents` | audit trail for the above | random |
| `epfTransfers` | balance moved between employers | random |
| `epfTransferEvents` | audit trail for the above | random |
| `epfInterestEntries` | one per establishment-financial-year | `{establishmentId}_{FY}` |
| `epfReconciliations` | observed EPFO balances | random |

### Deterministic ids are the idempotency mechanism

Three of these use a composed id rather than a random one, and that is load
bearing. A client-SDK Firestore transaction can read *documents* but **cannot
read queries**, so "has this month already been generated?" cannot be answered
by querying inside a transaction. Composing the id from the natural key makes
the question unnecessary: writing the same month twice overwrites rather than
duplicates.

This is why the monthly cron can be re-run safely, why the interest recompute on
opening the Balance tab cannot accumulate entries, and why a double-tapped save
does not create two rows.

The same constraint is why `epfProfile.activeEstablishmentId` exists: it is a
pointer a transaction *can* contend on, used to enforce "only one current
employment". Treat it as a write lock hint, never as business data — the real
answer comes from `findActiveEstablishment` over the loaded list.

### EPS is not EPF

`employerShare` is what the employer paid. `epfCredit` is what reached the PF
balance. They differ by the EPS (pension) slice, which goes to a different
scheme and **never enters the balance**. `contributionTotals()` in
`shared/features/epf/utils/contributions.ts` is the only place that derives
both, and tests assert the separation at row, establishment and portfolio level.

### One definition of balance

`establishmentBalanceBreakdown()` in `shared/features/epf/utils/transfers.ts` is
the single definition of an EPF balance: contributions, plus interest, plus
transfers in, minus transfers out, plus reconciliation adjustments. It was built
in KAN-69, extended in KAN-70 and consumed by KAN-71. Do not compute a balance
anywhere else — three competing numbers on three screens is the failure mode it
exists to prevent.

Its `interestEntries` and `adjustments` inputs are **required, not optional**,
deliberately: a caller who forgets them would silently under-report.

## Lifecycle

A contribution month moves through:

```
draft ──► confirmed ──► expected ──► credited
                                 ├─► partial
                                 ├─► missed
                                 └─► reversed
```

- **draft** — typed during backfill, not yet saved as real.
- **confirmed** — the user saved it as a historical fact.
- **expected** — generated by the scheduler for a month not yet credited.
- **credited / partial** — the credit landed, in full or short.
- **missed / reversed** — it did not land, or was undone.

`canTransition()` in `shared/features/epf/utils/lifecycle.ts` owns the legal
moves. Every change writes an `epfContributionEvent` recording `from`, `to`,
the actor (`system` for the cron, `user` for a person) and a reason.

**Auto-crediting is an assertion Spendly cannot verify.** When a month's credit
window has passed, the module marks it credited *as a projection*, never as a
confirmed fact, and the UI says so until someone reconciles it.

## Configurable rules

All effective-dated, all in `shared/features/epf/data/`:

| File | Holds |
|---|---|
| `epfRules.ts` | contribution slabs — 12% employee, 12% employer, 8.33% EPS, wage ceiling ₹6,500 → **₹15,000 from 2014-09-01** |
| `epfInterestRates.ts` | declared interest rate per financial year, 2010-11 → 2024-25 |
| `epfCreditWindow.ts` | when a credit is expected: days **15–25 of the following month** |
| `epfBatchLimits.ts` | Firestore batch sizing, with the invariant asserted |
| `epfClock.ts` | `Asia/Kolkata` — see below |

Slabs are chosen by the contribution month, not by today, so editing a historical
month applies the rule that was in force *then*.

**`findEpfInterestRate` returns `null` for an undeclared year, and that is
normal, not an error.** EPFO declares a rate months after the year ends. The
Balance tab shows "Rate not declared yet" and a dash rather than guessing — a
guessed rate would compound into every later year.

### The clock is IST, always

`epfClock.ts` hard-codes `Asia/Kolkata`. EPF is an Indian scheme: contribution
months, financial years and credit windows are defined in IST. Before KAN-72 the
client used the device timezone and the cron used UTC, so at 02:00 IST on the
1st they disagreed about which month it was. Both now call the same functions,
so they agree by construction.

A user in London still has an Indian EPF account with Indian month boundaries.
This is the domain's timezone, not a shortcut.

## The scheduler

Spendly runs on Firebase's Spark plan, which has no scheduled functions. So:

**GitHub Actions provides the clock, Netlify provides the compute.**

- `.github/workflows/epf-cron.yml` — `cron: "30 5 3 * *"` (11:00 IST on the 3rd)
  plus `workflow_dispatch`. It calls the function repeatedly, following
  `nextCursor` until null, capped at 200 pages.
- `netlify/functions/epf-cron.ts` — a paginated collection-group scan over
  `epfEstablishments` where `employmentStatus == "current"`, generating any
  months owed.

### Idempotency and recovery

Re-running is safe and is the recovery procedure. Because month ids are
deterministic, a second run writes the same documents and reports `written: 0`.
If a run fails halfway, **just run it again** — there is no partial state to
clean up, and the cursor only ever moves forward within a single invocation.

Someone who recorded a month years ago and nothing since can be owed hundreds at
once, so writes are chunked at `EPF_CRON_MONTHS_PER_BATCH` (200 months = 400
documents, inside Firestore's 500-write batch limit). The invariant is asserted
in `shared/features/epf/data/epfBatchLimits.test.ts` rather than left in a
comment.

The client has a safety net too: `useEpfCatchUp` fills any month the cron has
not reached, using the same pure planner, so the two cannot disagree.

### Authentication

A shared secret in a header, compared with `timingSafeEqual`. Rotating it means
updating **two** places: GitHub secrets and Netlify environment variables.

## Migration

**No data migration is required for any EPF collection**, and the reason is
worth stating precisely, because "the fields never changed" would be false.

Fields *were* added after the initial model: `archived` (KAN-65),
`epsMember`, `reconciledAt` (KAN-70), audit-event fields (KAN-72). Real data
written by v0.3.8 predates several of them.

Nothing needs migrating because **every read goes through a normalizer** that
treats an absent field as absent rather than asserting it is present:

```
normalizeEpfProfile · normalizeEstablishment · normalizeEpfContribution
normalizeTransfer   · normalizeInterestEntry · normalizeReconciliation
```

This is pinned by `shared/features/epf/utils/tolerantReads.test.ts`, which runs
every normalizer against an empty document, a v0.3.8-shaped document, a document
with unknown future fields, and a document with wrongly-typed values.

> KAN-73 closed the two places that did **not** normalize: the Netlify cron cast
> raw snapshots with `as Omit<EpfEstablishment, "id">`, and the profile was cast
> the same way in `useEpf.ts`. Both now normalize. **If you add a read, normalize
> it** — a cast is a claim about data you did not write.

### Rollback

Rolling back a release needs no data step. Older code reads newer documents
fine, because the normalizers ignore fields they do not know about. A field
added by a newer build simply goes unread until the build returns.

## Indexes

**No composite index is required anywhere in EPF.** The only index is a
collection-group single-field override on `epfEstablishments.employmentStatus`,
used by the cron, and it is deployed.

Every EPF query is unfiltered, single-document, or equality-only, and **no query
orders by a data field** — deliberately, because Firestore silently omits
documents missing the ordered field, which for financial history means quietly
losing a month. Sorting happens in memory over bounded collections.

> This is "no index is needed *for the queries that exist today*", not "EPF never
> needs indexes". A future `orderBy` on a data field will need one and will fail
> at **runtime**, not at build.

> **Always diff before deploying indexes.** `firebase deploy --only
> firestore:indexes` deletes anything absent from `firestore.indexes.json`, and
> a sibling repo shares this Firebase project. KAN-78 found six live indexes
> missing from the file; a blind deploy would have destroyed them.

Full audit: [`KAN-75-epf-index-query-review.md`](KAN-75-epf-index-query-review.md).

## Security

- Every collection is owner-scoped under `users/{uid}/`, covered by the
  recursive grant `match /users/{uid}/{collection}/{document=**}`. A narrower
  nested rule would be dead code — Firestore ORs nested matches.
- UAN, establishment number and member ID are **masked in the UI** and redacted
  from logs by `SENSITIVE_KEY` in `lib/errors.ts`.
- Masking is not encryption. These identifiers are plain text in the user's own
  Firestore documents, which is where they have to be for the app to work.

## Testing

### What is covered

Roughly **430 unit tests** across `shared/features/epf/` and the shared helpers
it uses: every calculation, every status transition, every validation, financial
year boundaries, IST month boundaries, transfers, interest, reconciliation,
portfolio aggregation, tolerant reads, and the net-worth roll-up.

`npm test` runs them; CI blocks a merge on them, on both typechecks, and on the
Firestore rules suite.

### What is not covered, and why

**There are no component or hook tests.** `vitest.config.ts` runs only
`shared/`, `services/`, `lib/` and `supabase/functions/`; `hooks/` and
`components/` are never collected.

This is a deliberate position, not an oversight. Introducing a second runner
(`jest-expo` + React Native Testing Library) on RN 0.86 / React 19.2 would mean
maintaining two test toolchains and mocking Firebase, expo-router and the theme
before asserting anything. The chosen alternative is to **keep decision logic
out of components**, where vitest already covers it — which is why the file
headers of `useEpf.ts`, `useEpfContributions.ts`, `useEpfTransfers.ts` and
`useEpfInterest.ts` all say they are deliberately thin.

The cost is real and worth naming: **rendering, wiring and navigation are
verified only by hand.** A component that computes nothing can still pass the
wrong prop. That is what the manual checklist below is for.

`shared/config/testScope.test.ts` guards the arrangement: a test file placed
outside every include glob fails the build instead of being silently skipped.

### Known drift, recorded rather than fixed

Found during the KAN-73 audit, deliberately left alone to keep the ticket
reviewable:

- Ten copies of a one-line `money` helper across `components/epf/`.
- Five hand-rolled singular/plural branches.
- Three minus-sign conventions (`−` U+2212 vs ASCII `-`) and three
  string→number policies.
- `withoutUndefined` also exists in `hooks/useSubscriptions.ts` and `chunk` in
  `hooks/useSpaces.ts` — both now have tested equivalents in `shared/utils/`
  that those files could adopt.
- `EpfCurrentMonthCard` and `EpfPortfolioCard` render nothing on error rather
  than showing an error state. Acceptable because a sibling component on the
  same screen surfaces it, but it means a failure there is invisible.
- The transfer action-visibility matrix and the lock arbitration inside
  `useEpf.ts` transaction closures need a Firestore mock to test meaningfully.

## Manual test checklist

Consolidated from the nine per-ticket guides. Run on Android **and** Web.

### Setup
1. Investments → existing tabs still work; an **EPF** tab appears.
2. EPF with no data → "Track your EPF" empty state → **Set up EPF**.
3. An 11-digit UAN shows "UAN must be exactly 12 digits" inline.
4. Add establishment A (employer, establishment number, member ID, joined date).
5. Add establishment B also marked "I still work here" → the conflict is shown
   inline; only one current employment is allowed.
6. Edit A → clear "I still work here" → set a leaving date before B's join date.
7. Archive A → it leaves the main list and appears under archived; restoring
   brings it back.
8. Deleting an establishment that has contributions is refused.

### Historical entry
9. Open an establishment → **Backfill**. For 2021-06 → 2024-08, 39 rows appear
   grouped by financial year.
10. Wage **25000** → 3,000 / 3,000 per month. Wage **12000** → pension **1,000**,
    not the capped 1,250.
11. Turn **Pension (EPS) member** off → pension 0 and the full employer share
    reaches EPF.
12. Edit one month by hand → the row is marked as edited, and **the saved totals
    match the shared computation** (no float drift).
13. **Save draft** → leave and return → rows persist as Draft.
14. **Save all** → rows become Manual. Saving again creates **no duplicates**.

### Scheduler
15. Trigger `epf-cron.yml` → the summary reports the **IST** month.
16. Trigger it a second time → `written: 0`.
17. A manually backfilled current month is **not** overwritten by the cron.
18. Calling the function with no secret header → **401**.
19. `epfContributionEvents` shows a `system` event for generated months and a
    `user` event for hand-saved ones.

### Lifecycle
20. With a wage recorded → **This month** card shows a projection. Remove the
    wage → it shows the warning instead, not a projection.
21. A month past its credit window reads **Credited · projected**.
22. **Record credit** with the expected amount → Credited. A lower amount →
    Partial.
23. **Mark as missed** and **Mark as reversed** both persist and do not advance
    further on reopening.

### Transfers
24. With two establishments where the previous has credited months → record a
    transfer. Same source and destination is rejected; so is a negative amount.
25. A new transfer shows **Initiated** and **balances are unchanged**.
26. **Complete transfer** → source falls, destination rises by the same amount.
27. Completing again from a stale screen is refused, not double-applied.
28. **Reverse** → a compensating transfer appears and the original is marked
    reversed.
29. **Confirm against EPFO** removes the "simulated" marker.

### Balance, interest, reconciliation
30. **Balance** tab lists interest by financial year with the rate used.
31. A year EPFO has not declared shows "Rate not declared yet" and a dash.
32. Leave and reopen → interest does **not** double.
33. **Record EPFO balance** higher than Spendly's → the variance is shown before
    saving; History rows are unchanged afterwards.
34. A second observation is kept alongside the first, newest first.

### Dashboard
35. **No EPF profile** → net worth unchanged, no EPF row, no extra listeners.
36. With EPF → an **EPF** row appears, reading "EPF · simulated" while anything
    is unconfirmed.
37. The EPF total sums every employer, **archived included**, and **pension is
    shown separately, outside the balance**.
38. Ghost mode hides the EPF total.
39. Accounts screen → the four breakdown cells wrap rather than clip on a narrow
    phone.

### States
40. On a narrow phone the five establishment tabs **scroll** rather than clip.
41. **Turn the network off on the Balance and Transfers tabs** → an error state
    with a working retry, not a confident wrong number. (Before KAN-73 a failed
    transfers listener rendered a balance silently missing every transfer.)
42. Back-date the device clock across midnight IST → the screens and the cron
    still agree on the month.
43. No EPF identifier appears in any log line during normal use.

## Troubleshooting

| Symptom | Cause | What to do |
|---|---|---|
| A month shows "Rate not declared yet" | EPFO has not declared that year's rate | Nothing. Add it to `epfInterestRates.ts` when declared. |
| The cron reports `written: 0` | Everything owed already exists | Nothing — this is the idempotency guarantee working. |
| A new month was not generated | No wage recorded on the establishment | The projector needs the most recent wage; record one. |
| "Multiple current employments" on save | Another establishment is open-ended | Set a leaving date on the other one first. |
| An establishment will not delete | It has contributions | Archive it instead. The guard fails closed. |
| Balance looks too low | A transfer out, or interest not yet recomputed | Open the Balance tab, which recomputes once per mount. |
| Balance and EPFO disagree | Expected — Spendly projects | Record the EPFO balance; the variance is kept as an adjustment. |
| Cron 401s | Secret rotated in only one place | Update **both** GitHub secrets and Netlify env. |
| A batch write fails | More than 500 documents in one batch | Check `epfBatchLimits.ts`; each row writes two documents. |

## Standing caveats

Two things are true at the time of writing and should be checked before trusting
the module in production:

1. **The deployed Netlify cron may still be running pre-KAN-72 code.** The IST
   fix, audit events and batch chunking are on `main` but reach production only
   through a *Deploy Web (Netlify)* run.
2. **KAN-69 through KAN-73 have never been exercised on a device.** v0.3.8
   (build 82) validated the module only through KAN-68. Everything since is
   covered by automated tests and typechecks alone — which is exactly the gap
   the manual checklist above exists to close.
